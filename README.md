# SaaS Admin Dashboard

A frontend portfolio project: a generic SaaS admin dashboard (users, revenue, plans) built to demonstrate data-fetching patterns, form validation, and role-based UI — as a companion piece to [Stride](#) (my e-commerce project), which focuses more on cart/state management.

**Live demo:** [saas-admin-dashboard-project.netlify.app]


## Features

- **Overview page** — KPI cards (revenue, active users, churn rate, avg session), a revenue-by-plan bar chart, and a snippet of the users list.
- **Users page** — full user list with plan filtering, paginated via a swipeable carousel view (grouped 4 per page).
- **Add User flow** — a validated form (React Hook Form + Zod) followed by a review/confirm step. Submitting adds the new user to the live list immediately — no page reload needed.
- **Reports page** — a larger revenue trend chart and a by-plan MRR/customer breakdown table.
- **Role-based UI (Admin/Viewer)** — switching roles hides admin-only actions (Add User, per-row remove) for Viewers, simulated entirely client-side via Context. This is a UI-layer simulation, not a real permissions/auth system — there's no backend to enforce it.

## Data layer

Everything is generated by [`@faker-js/faker`](https://fakerjs.dev/) in `src/Components/Data.jsx`, seeded (`faker.seed(42)`) so the dataset is identical on every load instead of reshuffling on refresh. Every "fetch" function (`fetchUsers`, `fetchRevenueByPlan`, etc.) is wrapped in a `Promise` + artificial delay to simulate real network latency — every component that consumes this data handles loading and error states the way it would against a real API, so swapping this layer for a real backend later wouldn't require touching component code.

Plan distribution is weighted (50% Starter / 35% Pro / 15% Enterprise) to loosely mirror a realistic SaaS customer base rather than an even split.

Added/removed users update in-memory state only (`UserContext`) — nothing persists across a page refresh, since there's no backend or `localStorage` layer here (Stride demonstrates the `localStorage`-persistence pattern instead).

## Tech stack

React 19 · Vite · Tailwind CSS 4 · React Router · React Hook Form + Zod · Recharts · Swiper · `@faker-js/faker`

## Architecture notes

- **Role state** lives in a shared `UserContext` (Context + state), since it's genuinely needed across scattered components (nav, table row actions, the Add User entry point).
- **`fetchRevenueByPlan`** is written as a pure function — it takes the user list as an argument rather than reaching into Context itself, so it has no hidden dependency on *how* it's called and would work unchanged if the data source changed.
- Derived UI values (like the filtered user list) are computed directly during render rather than duplicated into their own `useState` synced by a `useEffect` — avoids an unnecessary extra render cycle on every filter change.

## Known scope decisions

A few things were deliberately left out to keep this project finishable rather than an open-ended SaaS clone:

- The Add User flow is a single form + review/confirm step, not a multi-step wizard.
- The Users page filters by plan but doesn't support column sorting or free-text search.
- The revenue chart doesn't currently support click-to-drill-down into a specific plan.
- The Reports page doesn't have a date-range filter yet.
